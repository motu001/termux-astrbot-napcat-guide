## 第 1 关：Termux 与 Ubuntu

- [ ] Termux 来源可信，插件与主应用签名兼容；没有为了切换来源直接卸载未备份的旧环境。
- [ ] `pkg update` / `pkg upgrade` / 基础工具安装分别无错误，没有关闭签名验证。
- [ ] 手机报告 `aarch64`，有足够安装、缓存及备份空间。
- [ ] 实际记录 PRoot-Distro 版本和 `install --help`，没有混用 v4 插件别名与 v5 OCI 语法。
- [ ] 只有首次创建执行 `install`；旧实例不执行 `reset/remove`。
- [ ] 进入 `ubuntu` 后确认 `ID=ubuntu` 与 `arm64`；没有把提示符中的 root 当成 Android root。

**未通过：**停在下载/安装/架构错误处；不进 AstrBot 安装。

## 第 2 关：Ubuntu 中的 AstrBot

- [ ] uv 安装器来自 Astral 官方 HTTPS，下载不是错误页，审查/语法检查完成；知道自行计算的哈希不等于官方签名。
- [ ] `uv tool install astrbot --python 3.12` 成功；记录 `uv tool list`、`astrbot --version`。
- [ ] 在唯一、固定目录首次 `astrbot init`；确认 `.astrbot` 与 `data`，没有另建空实例。
- [ ] 运行前显式设置面板回环监听，未覆盖其他配置/泄露凭据。
- [ ] 服务从同一目录 `astrbot run`，管理页实际可达；初始管理凭据本人取得并修改。
- [ ] 会分离/恢复 tmux，知道 Ctrl+B、D 不等于 Ctrl+C/exit；没有启动重复实例。

**未通过：**保留错误，核对当前终端、工作目录、PATH、依赖；不以反复 `init` 修复。

## 第 3 关：Debian 中的 NapCat/QQ

- [ ] `napcat` 实例是 Debian、`arm64`；与 Ubuntu 的文件系统区分清楚。
- [ ] 使用专用安装器工作目录；保存官方提交和对应校验值。
- [ ] ARM64 QQ 下载真实成功，`file` / `dpkg-deb --info` 可解析，`Architecture=arm64`。
- [ ] QQ 版本与选定 NapCat 的兼容性有依据；没有用任意最新版/第三方包悄悄替换。
- [ ] 明确记录 QQ 是否有可信上游摘要；没有就写未取得，不伪造“签名验证成功”。
- [ ] NapCat ZIP 与官方 Release 资产摘要一致、`unzip -t` 通过。
- [ ] 下载失败时没有执行安装器，没有把 HTML/XML 改名为 `.deb`，没有使用 `--force` 解决 404。
- [ ] Shell 参数为本版本支持的 `--docker n --cli n --proxy 0`；不用 Docker/Podman/systemctl。
- [ ] 安装器依赖/解包/注入没有错误；检查 QQ 实际路径、大小写、执行权限与架构。
- [ ] 全新实例的数据工作目录固定、WebUI 明确回环监听；旧实例未未经备份迁移配置路径。
- [ ] `xvfb-run -a …/qq --no-sandbox` 真实运行且未立即退出；路径来自本次安装，不含未替换占位文字。

**未通过：**保持现有环境，暂停后续；绝不能把“脚本打印安装完成”替代 QQ 启动证据。

## 第 4 关：面板与 QQ 登录

- [ ] 本机 `6185` 与 `6099` 分别打开正确服务，凭据没有混用。
- [ ] 本人完成首次扫码/安全验证；录屏暂停或素材已遮盖有效二维码。
- [ ] 确认当前账号已登录且未离线，不只看账号头像或 HTTP 200。
- [ ] 实际监听范围已核对；`ss` 失败时记为待核验，不写安全通过。
- [ ] 没有为了电脑访问而开放公网、关闭认证或随意建立隧道。

## 第 5 关：OneBot 反向 WS

- [ ] AstrBot 是服务端；本手机监听地址和端口符合规划。
- [ ] NapCat 是 **WS 客户端**，URL 为实际端口的 `/ws`，不是管理页端口。
- [ ] 两端启用且 OneBot Token 完全一致；不是拿 WebUI Token/API Key 代填。
- [ ] 本次新增日志中出现真实连接，时间与本次操作对应；不是旧日志截图。
- [ ] 同时核对当前连接状态；没有把 `101` 字符串作为唯一标准。

## 第 6 关：消息与 AI 分层验收

- [ ] 模型类型、Base URL、模型 ID、额度来自本人的真实服务商资料，Key 未公开。
- [ ] 当前机器人实际选用了该模型，并完成一次模型连通性测试。
- [ ] 触发规则、允许列表、私聊/群聊范围明确；测试账号/群由本人授权。
- [ ] 另号发送一条无隐私消息，AstrBot 实际收到相应事件。
- [ ] 模型调用与这条消息能对应，成功结束；不是规则/插件固定回复。
- [ ] 出站发送成功与另号实际收到回复能对应。
- [ ] 脱敏证据只记录时间、状态、版本和必要标识，不发布完整对话/调用内容。

**只有相应层都通过才宣称 AI 对话成功。**框架启动、QQ 在线、模型测试、真实消息是不同验收项。

## 第 7 关：保活、恢复与开机

- [ ] Android 后台/省电设置按自己的手机实际操作；使用 wake lock 但不声称永不掉线。
- [ ] 先验证两个固定启动入口，没有重做安装/初始化或启动重复实例。
- [ ] 如使用本教程启动器：锁、维护标记、具名 tmux 会话、子进程不继承启动锁都符合示例。
- [ ] 如使用 Termux:Boot：签名兼容、点开一次、实际脚本已写入、执行权限正确，**不止 mkdir**。
- [ ] Boot 脚本调用的本机启动入口已经手动通过；知道退出码 0 不代表 QQ/模型健康。
- [ ] 经机主同意，真实停过 NapCat/QQ 并确认离线，再恢复；未点 UI/扫码却重新在线才算该次免点击。
- [ ] 经机主单独同意，真实重启 Android；记录是否需解锁、是否手动启动 Termux、入口是否系统触发。
- [ ] 整机重启后 QQ 登录、OneBot、另号消息和需要的 AI 路径分别通过。
- [ ] 多次测试分别记录；没有用一次服务重启代替整机自启/长期稳定性。

## 备份、升级和回滚

- [ ] 进入维护状态并正常停两服务，确认没有活动会话后再备份数据库/会话。
- [ ] 两环境和 Termux 控制入口均纳入计划；自定义外部绑定目录另有备份。
- [ ] 使用新时间戳目录；压缩文件检查和 SHA-256 校验通过。
- [ ] 异机副本私有且加密；没有仅把唯一备份留在将被卸载的 Termux 内。
- [ ] 更新前记录版本；一次只改一个组件；uv tool 安装版不从 WebUI 源码更新。
- [ ] 回滚前知道 `restore` 可能清理同名根目录，先校验并保留失败现场，不编造 `restore --name`。
- [ ] 做过真正的恢复演练，再逐层验收；不只凭归档可解压就写“恢复成功”。
