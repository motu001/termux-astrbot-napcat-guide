# 安全、故障排查、备份与回滚

> 与[从零安装与连接](从零安装与连接.md)配套，2026-10-03 核对。命令分别标注 Termux / Ubuntu / Debian；**不支持把源码核对当作实机验收**。上游版本、路径和确认方法见[上游参考](上游参考.md)。不要为了排错擅自重启手机、发 QQ 消息、清空会话或删除环境。

## 1. 哪些内容永远不进入公开视频/仓库

- QQ 账号、有效二维码、验证码、聊天记录；登录会话、设备信息及可能可恢复登录的备份。
- AstrBot 管理密码、NapCat WebUI Token、OneBot Token、模型 API Key、Cookie、SSH 私钥。
- 原始日志、完整配置文件、通知栏隐私、个人设备地址、私人镜像地址。即使“临时演示”也要脱敏。
- 备份不是公开安装包；`data`、NapCat 配置、QQ 的用户数据中可能含密钥和授权状态。不要复制到 Git 管理目录后仅依赖 `.gitignore`。

凭据由本人在自己的设备上设置/取得。本仓库没有通用密码。示意图必须标“示意”；实际扫码时暂停录屏，不能等发布后再补救。若密钥已入库或公开，**先轮换/吊销**，再处理泄露副本；删除最新一份文件不会抹去 Git 历史。

### 管理面板的监听范围要实际检查

- 上游默认值不都是回环：本次 AstrBot 默认配置中 `dashboard.host=0.0.0.0`，NapCat `v4.18.28` WebUI 默认 `host=::`。后者也不是 IPv6 回环 `::1`。
- 本教程新装时显式设置面板为 `127.0.0.1`。**访问 localhost 与仅监听 localhost 是两件事**；旧实例不能因为浏览器地址是回环就视为安全。
- 同手机 OneBot 反向 WS 服务端也优先监听 `127.0.0.1`。两端使用相同的独立高熵 Token，不复用 WebUI Token/模型 Key。
- 不为排障绑定公网、不关闭鉴权、不打开路由器端口映射、UPnP 或临时公网隧道。PRoot 不是安全沙箱，`--no-sandbox` 也不是安全增强；不可信插件仍可读取进程可见文件。
- 需要电脑管理时，优先通过自己配置的 SSH 回环转发；SSH 端口与三个服务端口不是同一回事。没有安全访问需求就不安装/开启 SSH。

**只读检查，位置：Termux。**

```sh
ss -ltn | grep -E ':(6185|6099|6199)([[:space:]]|$)'
```

若 Android 限制了 socket 枚举，命令可能报权限错误；这既不证明端口关闭，也不证明仅监听本机。回看应用实际启动信息和本地配置，不能把检查失败当作“安全通过”。

## 2. 故障排查：在哪层失败，就停在哪层

顺序：**所在终端 → 架构/空间/下载 → 程序启动 → 面板 → QQ 在线 → OneBot → 入站消息 → 模型调用 → 出站回复**。不跨层跳结论。

| 现象 | 下一步检查 | 不要做 |
|---|---|---|
| `pkg: not found` | 核对 `cat /etc/os-release`，可能在 Ubuntu/Debian；新开 Termux 会话，别关运行中的服务 | 到所有环境重复安装 Termux 工具 |
| `apt-get` 报错 | 先确定是系统识别、网络、签名还是包缺失；只处理当前错误 | 仅凭这一条报错认定当前环境、关闭仓库签名检查 |
| `ubuntu:24.04`/`--name` 不支持 | `dpkg-query -W proot-distro`、`proot-distro install --help`；v4 插件别名与 v5 OCI 语法不同 | 对已有环境 `reset/remove`，或盲改成另一条教程 |
| ARM64 手机遇到 `Exec format error` | `uname -m`、`dpkg --print-architecture`、`file` 检查二进制 | 把 AMD64/x86_64 包当原生 ARM64，宣称可原样运行私有镜像 |
| 下载 403/404/`NoSuchKey` | 确认官方来源、HTTP 状态、文件内容类型和体积；curl 使用 `-fL` | 把 HTML/XML 改名 `.deb`；加 `-k`；随机下载网盘包 |
| `not a Debian format archive` | `file QQ.deb`、`dpkg-deb --info QQ.deb`；通常应先查下载结果，具体原因按内容确认 | 继续解包、强制安装或重复重启 |
| uv/AstrBot 依赖安装失败 | 保存具体错误；核对 Python 3.12、ARM64 wheel/编译依赖、内存/磁盘和网络 | 混用 uv tool、源码 venv、系统 pip 三套安装 |
| `astrbot: not found` | Ubuntu 中 `export PATH="$HOME/.local/bin:$PATH"`，再看 `uv tool list` | 在 Debian 再装一份 AstrBot 作为“修复” |
| `not a valid AstrBot root directory` | 回到首次 `init` 的目录；本教程为 Ubuntu 的 `/root/astrbot`，检查 `.astrbot` | 在任意目录再次 `init` 导致空配置 |
| AstrBot 锁获取失败/端口占用 | `tmux list-sessions`、`proot-distro ps`、实际监听与进程身份；先排查重复实例 | 删除锁文件、`pkill -f qq/python/proot`、强杀无关任务 |
| `systemctl` 提示没有 systemd | 这是无 root PRoot；使用已核对的前台启动命令和 Termux tmux | 给 systemctl 加 sudo、在 PRoot 内硬装 Docker/Podman |
| `xvfb-run` 不存在或 QQ 立即退出 | 安装器依赖是否真的成功；`command -v xvfb-run`、QQ 文件架构、当次错误 | 宣称“安装器结束所以服务已启动” |
| `6185` 或 `6099` 打不开 | 对应 tmux 会话是否还活着、程序是否退出、实际端口/监听；HTTP 状态与应用日志一起看 | 两个面板互换端口、开放公网试一试 |
| WebUI Token 无效 | 私下确认进入的是哪个实例/端口，用该次运行的管理 Token；检查环境覆盖项 | 用 OneBot Token 或模型 Key 登录；公开配置求助 |
| QQ 页面出现账号但未在线 | 查询/查看当前已登录和离线状态；安全验证由本人完成 | 把缓存账号、二维码消失、HTTP 200 当作在线 |
| QQ 在线但 OneBot 未连 | NapCat 必须是 WS 客户端；目标 `ws://127.0.0.1:6199/ws`；AstrBot 监听、同一 Token、启用状态 | 用 `6099/6185` 作目标、漏 `/ws`、把 `0.0.0.0` 作客户端目的地址 |
| OneBot 连上但无消息事件 | 测试号/目标账号、当前实例、允许列表、群/私聊/触发规则 | 为测试向不知情群聊群发消息 |
| 能收到事件但模型报错 | 当前实例是否选中模型、Base URL/模型 ID、权限/额度、超时；私下检查服务商记录 | 将 Key 写进命令行截图或公开日志 |
| 收到了固定回复但无模型记录 | 区分规则/插件回复与真实模型路径 | 在视频中把 `/help` 回复算作 AI 生成 |
| 两个相似 NapCat 页面 | 核对端口、工作目录、PID/启动时间和转发；可能是同一服务的两入口或不同实例 | 凭页面相似就删目录 |
| 熄屏/重启后离线 | 分查 Android 保活、自启动入口、服务进程、网络、QQ 授权状态 | 无限登录重试、自动清空会话 |

### 当前已知：官方安装器内 QQ 下载链接失效

2026-10-03 对官方提交 `dc414ee6cff988b137ee8636caebdcd68288e64d` 中 ARM64 QQ 包地址进行 HEAD 请求，返回 **HTTP 404 / application/xml**。这只是本次网络读取结果，但足以否定“这条 URL 当前已下载验证成功”的说法。

QQ Linux 官网另公布了 **3.2.34（2026-09-24）** 的 ARM64 新直链，官网与其下载配置均可读取；本环境对新包 HEAD、Range 和本机 curl 复查为 **403/0 字节**，未验证包格式或兼容性。不能把旧 404 推断为所有官方包不可用，也不能把官网有链接当成已下载成功。准确 URL、请求结果与源码见[上游参考](上游参考.md)。

主教程因此在运行安装器前增加下载、格式、架构、哈希检查及新包候选的停止条件。该安装器只支持复用当前目录名为 `QQ.deb` 的文件，没有核实到本地包路径参数；对已有 QQ 版本配置还可能写入固定旧目标，不能盲用新包修复旧实例。上游 issue 的用户报告只能作为线索，不是可信二进制来源或已修复证明。若本机无法取得通过检查的候选包，或无法继续兼容性试装：**停在安装关卡并保留环境**，不静默换镜像/架构/路线。

### `failed_auth` 不能单独诊断根因

原机 2026-10-02 服务重启记录中曾出现 `failed_auth`，后来状态确认在线、助手返回 `already_login`。中间错误原因未被单独诊断，不能据字符串就认定 Token 错误、限流或会话失效。先查实际状态、时间范围和对应实例；需要重新验证身份时由机主处理。

## 3. 备份：先停止写入，再备份两环境与 Termux 控制入口

本节具体命令针对主教程的 **PRoot-Distro v5.9.0 + `ubuntu`/`napcat` 两个实例**。不同版本先看 `backup --help`、`restore --help`、`rename --help`，不猜参数。

### 3.1 记录版本，进入维护状态

私下记录：Termux 与 PRoot-Distro 版本、两个系统版本、AstrBot/uv 版本、NapCat Release、QQ 版本、安装器提交/包哈希、实例工作目录、端口、启动入口。**不要把账号与密钥抄进公开版本清单**。

若采用主教程启动器，**位置：Termux**，先创建维护标记；同一把锁避免与正在启动的入口竞争：

```sh
(
  set -eu
  umask 077
  mkdir -p "$HOME/.cache"
  exec 9>"$HOME/.cache/phone-bot-start.lock"
  flock -w 30 9
  : > "$HOME/.phone-bot-maintenance"
  printf '已设置维护标记；接下来人工停止两服务。\n'
)
```

这只让**读取这个标记的启动器**暂停启动，不会停止已运行服务。旧机另有定时器/开机恢复入口时，需先按其自身机制暂停，不能认为所有守护器都受此标记控制。

### 3.2 正常停止服务并确认

分别 `tmux attach-session -t napcat` / `tmux attach-session -t astrbot`，在确认是本教程对应服务后用 Ctrl+C 请求停止，等待退出。关闭额外进入这些环境的交互 shell；不能仅 detach 就备份仍在写入的数据库。

**位置：Termux。**

```sh
proot-distro ps
tmux list-sessions
```

✅ 两个实例不再有活动 PRoot 会话、对应服务已停止。异常卡住时先保存诊断、核对具体 PID 和进程树；本文不提供宽泛进程名强杀。所有 QQ/模型数据都留在私有环境中。

### 3.3 创建带时间戳的完整备份并检查

**位置：Termux。**下例拒绝在活动会话仍存在时备份；仅管理本教程两个实例。备份写进 Termux 私有 HOME，不写进仓库或公共相册。

```sh
(
  set -euo pipefail
  umask 077
  test -f "$HOME/.phone-bot-maintenance"
  sessions="$(proot-distro ps)"
  if printf '%s\n' "$sessions" | awk '$2 == "ubuntu" || $2 == "napcat" {found=1} END {exit !found}'; then
    printf '仍有活动会话，停止备份。\n' >&2
    exit 1
  fi
  BACKUP_DIR="$HOME/phone-bot-backups/$(date +%Y%m%d-%H%M%S)"
  test ! -e "$BACKUP_DIR"
  mkdir -p "$BACKUP_DIR/termux-control"
  proot-distro backup --output "$BACKUP_DIR/ubuntu.tar.gz" ubuntu
  proot-distro backup --output "$BACKUP_DIR/napcat.tar.gz" napcat
  for rel in bin/start-phone-bot .termux/boot/50-phone-bot.sh; do
    if [ -f "$HOME/$rel" ]; then
      mkdir -p "$(dirname "$BACKUP_DIR/termux-control/$rel")"
      cp -p "$HOME/$rel" "$BACKUP_DIR/termux-control/$rel"
    fi
  done
  tar -czf "$BACKUP_DIR/termux-control.tar.gz" -C "$BACKUP_DIR" termux-control
  cd "$BACKUP_DIR"
  gzip -t ubuntu.tar.gz napcat.tar.gz termux-control.tar.gz
  sha256sum ubuntu.tar.gz napcat.tar.gz termux-control.tar.gz > SHA256SUMS
  sha256sum -c SHA256SUMS
  printf '备份完成，请私下记录目录：%s\n' "$BACKUP_DIR"
)
```

全环境备份保留 AstrBot 实例、uv 环境、NapCat 安装/配置以及**存于环境内部**的 QQ 用户数据，避免只拷 `webui.json` 却漏会话/数据库。外部绑定目录、外置存储与 Termux 应用本身不自动包含在环境备份中；有自定义绑定就单独纳入计划。

**检查通过不等于可恢复已验收**：哈希与 gzip 测试能发现部分文件损坏，但仍需恢复演练。QQ 会话是否仍有效由上游决定，不能承诺恢复归档就免认证。

- 再做一份私有、加密、受访问控制的异机备份；先确认容量和目标位置，不自动上传。
- 不把明文 tar 放进公开云盘、GitHub、聊天附件或公开视频素材目录。
- 更换 Termux 安装来源、卸载应用或清理数据前，先确认异机副本可读。只保存在 Termux HOME 的备份可能随卸载一起丢失。

## 4. 升级：一次改一个组件

1. 完成上节停机备份；记录当前可用版本和实际备份目录，保留旧安装包/发布摘要（仅官方公共包）。
2. 阅读目标版本的官方发行说明和兼容性要求。不要假定 AstrBot、NapCat、QQ 任意最新版都能组合。
3. 保持维护标记。只启动维护 shell，不启动机器人服务。
4. **uv tool 安装的 AstrBot** 在 Ubuntu 中升级，不用 WebUI 的源码更新按钮：

```sh
export PATH="$HOME/.local/bin:$PATH"
uv tool upgrade astrbot --python 3.12
```

```sh
cd "$HOME/astrbot"
astrbot --version
```

不重新执行 `init`，不把数据搬到新目录。依赖安装失败就停止，不继续升级另一组件。

5. **NapCat/QQ** 升级重新走官方来源、包格式/架构/摘要及兼容性检查。当前固定安装器可能覆盖现有内容，`--force` 不是例行参数；不要在运行中的 QQ 上直接覆盖。保留原数据路径、Token 和会话，不用一套“新默认配置”替换旧配置。
6. 退出维护 shell、确认没有其他入口竞争后解除维护，再从原入口手动启动。**位置：Termux，只删除这个明确的标记文件：**

```sh
rm -f "$HOME/.phone-bot-maintenance"
"$HOME/bin/start-phone-bot"
```

未安装该启动器时使用主教程原来的两个 tmux 启动命令。逐层复测：面板、QQ 在线、OneBot、入站、模型调用、出站。更新成功不等于旧插件/模型配置都兼容。

7. 失败时重新进入维护、停服务，按下节回滚。数据库可能已迁移，**仅把 Python 包降级不一定能兼容新数据**；优先恢复一致的升级前环境与数据。

## 5. 回滚：保留失败现场，不直接覆盖现有环境

PRoot-Distro **v5.9.0 的 `restore` 会清空归档中同名的现有环境根目录**，不是只补缺失文件；也没有本教程可用的 `restore --name` 选项。因此先停服务、验证备份，再将原环境改名保留，最后恢复原名称。

只恢复自己的可信归档；确认空间够同时存放归档、失败现场和恢复环境。先完成 3.1—3.2，维护标记保持存在；关闭其他自动恢复入口。下面每块单独执行，**任何失败都停下记录已完成的改名，不整段重跑**。

**位置：Termux。**

```sh
read -r -p '粘贴升级前备份目录的绝对路径：' BACKUP_DIR
```

```sh
(cd "$BACKUP_DIR" && sha256sum -c SHA256SUMS)
```

```sh
tar -tzf "$BACKUP_DIR/ubuntu.tar.gz" | sed -n '1,6p'
tar -tzf "$BACKUP_DIR/napcat.tar.gz" | sed -n '1,6p'
proot-distro ps
proot-distro list
```

✅ 备份来自目标实例，归档顶层分别对应 `ubuntu`、`napcat`；没有活动会话；现有实例名称确认无误。目录名列表也只供私下检查。

```sh
ROLLBACK_STAMP="$(date +%Y%m%d-%H%M%S)"
printf '保留现场后缀：%s\n' "$ROLLBACK_STAMP"
proot-distro rename ubuntu "ubuntu-before-rollback-$ROLLBACK_STAMP"
```

```sh
proot-distro rename napcat "napcat-before-rollback-$ROLLBACK_STAMP"
```

```sh
proot-distro list
```

✅ 旧环境以新名称保留，`ubuntu`、`napcat` 原名称已空出来。若不是这个状态，先调查，不运行恢复。

```sh
proot-distro restore "$BACKUP_DIR/ubuntu.tar.gz"
```

```sh
proot-distro restore "$BACKUP_DIR/napcat.tar.gz"
```

恢复完成后核对版本、原工作目录和本地配置，**不重做初始化、不公开会话**。若这次升级也改动了 Termux 控制脚本，先对照归档中的 `termux-control` 副本，仅恢复本教程的两个明确文件；不要对整个 Termux HOME 盲目解压覆盖。主教程脚本未改时无需恢复它们。

解除维护，按原入口手动启动，逐层验收。不要启动 `*-before-rollback-*` 中的机器人副本，否则相同端口/账号可能冲突；在确认恢复可靠前也不要删除这些失败现场。

**真正的恢复演练通过条件：**从停机/备份恢复后，版本与数据一致、账号状态经过本人确认、OneBot 连接、真实测试消息与所需模型路径都通过。单纯 `restore` 返回 0 不能写成“机器人恢复成功”。

## 6. 自启问题单独查，不与安装问题混在一起

顺序：Termux:Boot 与主应用签名兼容 → 插件已点开一次 → `~/.termux/boot/` 脚本可执行 → 正确的 Termux shebang/PATH → 没有维护标记/重复启动器 → 两服务起来 → 网络可用 → QQ 授权 → OneBot → 消息。

开机入口只创建 tmux 会话，不证明 QQ 已登录。参见[开机自启与 QQ 自动登录](开机自启与QQ自动登录.md)；现有 2026-10-02 证据仅为服务重启免点击登录，不能替代 Android 冷启动无人值守验收。需要用户解锁或扫码时如实记录，不能剪掉这些动作。
