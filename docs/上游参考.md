官方说明要求插件与主应用签名兼容；Termux:Boot 安装后要点开一次，脚本放在 `~/.termux/boot/`，多个脚本按排序执行，可先调用 `termux-wake-lock`。这些是软件入口条件，不等于所有手机都能在未解锁/断网/省电限制下自动上线。

教程选择先让用户手动验证本机启动入口，再接 Boot。文档中的 `start-phone-bot` 是为本教程编写的受限示例，不是 Termux 官方健康监控程序，也不是原机私有恢复脚本。

## S2. PRoot-Distro：版本语法与能力边界

- [官方 v5.9.0 README](https://github.com/termux/proot-distro/blob/v5.9.0/README.md)
- [官方 v5.9.0 Release](https://github.com/termux/proot-distro/releases/tag/v5.9.0)
- [Termux 官方包配方](https://github.com/termux/termux-packages/blob/master/packages/proot-distro/build.sh)
- [历史 v4.38.0 README](https://github.com/termux/proot-distro/blob/v4.38.0/README.md)

本次包配方 `TERMUX_PKG_VERSION="5.9.0"`，Release 发布于 2026-09-19 UTC；只代表核对时源仓库状态，镜像站和读者本机可能不同。

- **v5.9.0：**`install [OPTIONS] IMAGE/PATH` 可直接取公共 OCI 镜像；`--name` 指定本地实例名，`--override-alias` 仍作为弃用的兼容长参数接受。
- **v4.38.0：**发行版插件别名模式，例如 `install ubuntu`、`install --override-alias napcat debian`；不能由此推出支持 `ubuntu:24.04` 这样的任意 OCI 标签。
- 读取/解包 OCI 层不等于运行 Docker Engine。PRoot 的系统调用转译不提供 Docker 所依赖的完整内核隔离功能，本文不把无 root PRoot 内的 Docker/Podman 当可行主线，不用 systemctl 管理应用。
- v5.9.0 提供 `ps`、`rename OLDNAME NEWNAME`、`backup --output FILE NAME`。**`restore FILE` 会清理归档内同名的现有根目录**；不是无损合并，不支持本文所谓的 `restore --name`。教程因此先停机、校验备份、改名保留失败环境，再恢复原名称。

本教程保留 Ubuntu `24.04` 与 Debian `stable` 主线；后者为浮动标签，实际系统版本必须记录。固定为 `bookworm` 只是另一种版本选择，应在口播/记录中明确，不应静默替换，也不宣称任何版本对所有手机最佳。新机按实际 `--help` 选择语法；已有环境升级应先做自己的完整备份。

- [NapCat 官方 Shell/Termux 指南](https://napneko.github.io/guide/boot/Shell)

- [同一提交的 Termux 安装器](https://github.com/NapNeko/NapCat-Installer/blob/dc414ee6cff988b137ee8636caebdcd68288e64d/script/install.termux.sh)
- [QQ Linux 官方下载入口](https://im.qq.com/linuxqq/index.shtml)

Linux 安装器本次固定提交为 `dc414ee6cff988b137ee8636caebdcd68288e64d`：

1. 将 `aarch64` 映射为 `arm64`，存在 ARM64 `.deb` 分支。Shell 安装参数 `--docker n --cli n --proxy 0` 可在实际参数解析/帮助中找到；`--cli` 只控制附加 TUI 工具，不代表 QQ 是否运行。
2. 当前用户安装目录是 `$HOME/Napcat`，QQ 可执行文件为 `$HOME/Napcat/opt/QQ/qq`。它打印的前台形式是 `xvfb-run -a …/qq --no-sandbox`，不需要编造 `systemctl start napcat`。
3. 安装器会复用当前工作目录已有的 `QQ.deb` 与 `NapCat.Shell.zip`，同时会清理临时文件；因此主教程使用专用工作目录、先下载校验，不在已有项目目录直接执行。
4. 脚本包含 `curl -k` 下载分支，不能据“官方脚本”四个字就宣称所有下载都验证 TLS。主教程显式使用验证证书的 HTTPS 下载，并在运行前检查本地包；这仍不是一次完整供应链审计。
5. 固定脚本的 QQ 目标为 `3.2.30-50828`。[旧 ARM64 地址](https://qqdl.gtimg.cn/qqfile/QQNT/9.9.32/beta/727ce4e5/linuxqq_3.2.30-50828_arm64.deb)本轮 **HEAD 返回 404，Content-Type 为 application/xml**；这不是官方所有包均失效的证明。官网下载页仍公布新包，具体可达性见下段。
6. 官方 Termux 包装脚本包含初始化失败后 `proot-distro remove napcat` 的分支，并展示旧式根目录布局。它可以作为另一入口的参考，**不能当已存在 `napcat` 环境的通用修复命令**，本教程不改用它替代 Debian 手动路线。

### QQ 官网新直链与本次请求结果（不能与旧 404 混称）

[QQ Linux 官网](https://im.qq.com/linuxqq/index.shtml)的 HTML 直接加载 [官方下载配置 linuxConfig.js](https://cdn-go.cn/qq-web/im.qq.com_new/latest/rainbow/linuxConfig.js)。本轮这两项均 HTTP 200；配置中的 `version` 为 `3.2.34`、`updateDate` 为 `2026-09-24`，`armDownloadUrl.deb` 指向：

```text
https://qqdl.gtimg.cn/qqfile/QQNTV2/9.9.36/release/9ee04bef/QQ_3.2.34_260924_arm64_01.deb
```

| 请求 | 本执行环境实际观测 | 证据边界 |
|---|---|---|
| 新包 HEAD | HTTP 403，Content-Length 0 | 不代表所有读者网络均失败；原因未确认 |
| 新包 GET，Range `bytes=0-131071` | HTTP 403，正文 0 字节，无 Content-Range | 没有 DEB 的 `!<arch>` 包头或 control 元数据可验证 |
| 携官网 Referer 的 Range `bytes=0-4095` | HTTP 403，正文 0 字节 | 没有获得格式、架构或完整摘要证据 |
| 本机 `curl.exe --head --location` 复查 | HTTP 403，Content-Length 0 | 与上述网络结果一致，不构成全球不可用结论 |

因此正确说法是“**官方公布了更新 ARM64 包，但本环境尚未下载和运行验证**”，而不是“官方无包可用”或“新版已修好”。主教程给出仅下载候选包并检查格式/架构的命令；下载失败就停止。未执行完整下载，不能给新包编造 SHA-256 或 `dpkg-deb` 通过记录。

安装器的本地包支持来自 `install_linuxqq_rootless` 中的文件存在判断：当前工作目录的 **`QQ.deb`** 存在就跳过下载、解包，之后会删除此工作副本。没有核实到 `--local-qq`、`--qq-package` 等参数；`--qq` 在其帮助中是 Docker 模式账号参数，不是包路径。源码还在解包后以固定旧目标调用 `update_linuxqq_config`：**已有** `$HOME/.config/QQ/versions/config.json` 时会写入旧 `baseVersion/curVersion/buildId`；文件不存在时跳过。故新版本地包可作为全新实例的待验证试装候选，不可宣传为对已有实例的通用修复。
