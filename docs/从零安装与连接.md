# 手机从零部署 QQ 对话机器人：Termux + AstrBot + NapCat

> **执行分工：**本页是详细执行手册，默认供已获得实际终端/SSH权限的Agent读取并执行。人先完成[必要准备与交接](人做准备_Agent接手.md)，然后交付[Agent任务书](../AI_协助部署_复制给AI.md)。文中逐块命令由执行者操作，不代表必须让人逐条复制和回报；本人认证或超出授权时才回交。

## 0. 开始之前：准备、位置、端口

### 0.1 需要什么

- ARM64 Android 手机、稳定网络、可用于测试的 QQ 号，以及本人能够完成扫码/安全验证的方式。`uname -m` 应为 `aarch64`，Linux 包架构应为 `arm64`。
- **容量规划建议而非最低配置保证：**安装前尽量留出 12 GB 以上空间；两个系统、下载缓存、聊天数据和备份会继续增长。完整备份与回滚另需空间，不要只剩几百 MB 时开始。
- 充电、散热和可信网络。长期插电注意温度、电池健康，不把手机盖在被褥中运行。
- 如需 AI 对话，自行准备模型服务商的账号、额度及 API Key；部署框架不代表模型调用免费。
- 本机浏览器即可操作面板，电脑可选。安装 Termux/插件要遵守同一来源、兼容签名的要求；已有环境先备份，不为换安装来源直接卸载 Termux。

### 0.2 四种操作位置

| 本文标记 | 怎样确认 | 使用的命令/操作 |
|---|---|---|
| **Termux** | `printf '%s\n' "$PREFIX"` 通常显示以 `/data/data/com.termux/files/usr` 结尾的目录；`pkg --version` 可用 | `pkg`、`proot-distro`、`tmux`、开机入口 |
| **Ubuntu** | `cat /etc/os-release` 中 `ID=ubuntu` | `apt-get`、`uv`、AstrBot |
| **Debian** | `cat /etc/os-release` 中 `ID=debian` | `apt-get`、NapCat 安装器、Linux QQ |
| **手机浏览器/QQ** | 浏览器地址栏、自己的 QQ 客户端 | 管理、扫码、设置、测试 |

`root@...` 只是 PRoot 内的用户身份，**不表示手机已经 root**。Ubuntu 和 Debian 是不同文件系统；两边都有 `/root`，内容不相同。PRoot 默认共享手机网络，没有 Docker 的独立网络栈和端口映射。

**复制规则：**一次一个代码块，等它结束、核对输出，再执行下一个。代码块不带 `$` 提示符；不要把讲解文字一起粘贴。遇到错误立即停在当前关卡，不继续堆命令。长期运行的服务不返回提示符通常正常；不要往其日志窗口继续粘贴安装命令。

### 0.3 三个服务端口不要混用

| 地址/端口 | 谁监听、用途 | 谁访问 |
|---|---|---|
| `http://127.0.0.1:6185/` | AstrBot 管理面板；本教程显式设为回环监听 | 手机浏览器 |
| `http://127.0.0.1:6099/` | NapCat WebUI；本教程显式设为回环监听 | 手机浏览器 |
| `ws://127.0.0.1:6199/ws` | AstrBot OneBot v11 反向 WS 服务端 | NapCat 的 **WebSocket 客户端**，不是浏览器首页 |
| SSH 端口（可选） | Termux SSH 管理/转发，与前三个无关；具体端口查自己的 SSH 配置 | 可信电脑；本机安装不需要开 SSH |

浏览器里填写 `127.0.0.1` **不会自动收紧服务的监听地址**。核对的上游默认值中 AstrBot 是 `0.0.0.0`，NapCat 是 `::`，均不能解释为仅本机。本文在启动前设置回环地址；端口实际值仍要查当次日志。电脑上的 `127.0.0.1` 是电脑，不是手机。

```text
QQ 消息
   ↕
Debian PRoot：Linux QQ + NapCat
   └── WS 客户端 ──> ws://127.0.0.1:6199/ws
Ubuntu PRoot：AstrBot
   └── 按配置调用模型服务，生成回复后经 NapCat 发回 QQ
Termux：管理两个 PRoot 环境与 tmux 会话
```

[部署检查清单](部署检查清单.md)用来逐项勾选；需要 AI 陪跑时使用[AI 协助部署任务书](../AI_协助部署_复制给AI.md)。只回报关卡、位置、脱敏错误和成功信号，不发 Token、二维码、完整配置或原始日志。

## 第 1 关｜安装 Termux，识别 PRoot-Distro 版本，进入 Ubuntu

### 1.1 安装应用

从 [Termux 官方安装说明](https://github.com/termux/termux-app#installation)选择 GitHub Releases 或 F-Droid 等官方列出的来源。本教程后续要用 Termux:Boot 时，**主应用与插件必须签名兼容**；不要混装不同来源的构建。第一次打开 Termux 等待初始化。

### 1.2 更新和安装基础工具

**位置：Termux。**每块都要没有错误，再继续。

```sh
pkg update
```

```sh
pkg upgrade -y
```

```sh
pkg install -y proot-distro tmux curl coreutils util-linux iproute2
```

```sh
uname -m
df -h "$HOME"
dpkg-query -W proot-distro
proot-distro install --help
```

✅ 看到 `aarch64`、足够空间及本机安装版本。包管理器签名失败、空间不足、下载失败都不算通过；不要关闭签名检查。`pkg: not found` 时先确认是不是误进了 Ubuntu/Debian。

### 1.3 先区分版本，再安装

本次官方 Termux 包配方和 PRoot-Distro Release 为 **5.9.0**。以下主线采用其镜像语法。镜像来自发行版的公共 OCI 仓库；只是提取用户态文件系统，**不是在 Android 上运行 Docker Engine**。

| 官方版本资料 | Ubuntu 安装语法 | Debian 实例命名语法 |
|---|---|---|
| 本次核对的 `v5.9.0` | `proot-distro install ubuntu:24.04 --name ubuntu` | `proot-distro install debian:stable --name napcat` |
| 历史 `v4.38.0`，仅供识别旧教程 | `proot-distro install ubuntu` | `proot-distro install --override-alias napcat debian` |

**不要两行都执行。**v4 的发行版插件决定具体系统版本，不支持把 v5 的任意 OCI 标签原样套进去。v5 仍接受旧参数别名，也不代表两个版本的镜像处理方式完全相同。新机更新后帮助仍不支持主线语法，就停下来核对来源/版本；已有 v4 环境先备份和查迁移说明，不能用 `reset/remove` 当升级办法。

**位置：Termux，新装且没有 `ubuntu` 实例时。**

```sh
proot-distro list
```

```sh
proot-distro install ubuntu:24.04 --name ubuntu
```

```sh
proot-distro login ubuntu
```

**现在位置变为 Ubuntu。**

```sh
cat /etc/os-release
uname -m
dpkg --print-architecture
```

✅ `ID=ubuntu`、版本符合选择、架构 `aarch64` / `arm64`。下载成功不等于进入成功；进入成功也不等于 AstrBot 已装好。以后只用 `login ubuntu` 进入，**不重复 install**。

### 2.3 首次运行前限制面板监听

**位置：Ubuntu 的 `/root/astrbot`；此时服务尚未运行。**下面只设置 `dashboard.host`，保留其他配置，不打印任何凭据。旧实例应先按[备份步骤](安全与故障排查.md)停服务备份，不能边运行边改配置。

```sh
python3 - <<'PY'
import json
from pathlib import Path
p = Path('data/cmd_config.json')
cfg = json.loads(p.read_text(encoding='utf-8-sig')) if p.exists() else {}
if not isinstance(cfg, dict):
    raise SystemExit('配置不是对象，停止；不要覆盖')
dashboard = cfg.setdefault('dashboard', {})
if not isinstance(dashboard, dict):
    raise SystemExit('dashboard 格式异常，停止；不要覆盖')
dashboard['host'] = '127.0.0.1'
p.write_text(json.dumps(cfg, ensure_ascii=False, indent=2) + '\n', encoding='utf-8')
p.chmod(0o600)
print('dashboard.host 已设置为 127.0.0.1；未输出密码')
PY
```

### 2.4 保存启动入口，使用 tmux 运行

**位置：Ubuntu。**此文件是本教程新建的本机启动入口，不是原机私有脚本。已存在时停止检查，不覆盖。

```sh
(
  set -eu
  test ! -e "$HOME/start-astrbot.sh"
  cat > "$HOME/start-astrbot.sh" <<'SH'
#!/bin/sh
set -eu
umask 077
export PATH="$HOME/.local/bin:$PATH"
cd "$HOME/astrbot"
test -f .astrbot
exec astrbot run
SH
  chmod 700 "$HOME/start-astrbot.sh"
)
```

```sh
exit
```

**回到 Termux。**确认没有同名会话、没有另外一份 AstrBot 正在运行后启动：

```sh
tmux list-sessions
```

第一次显示“没有运行的 server/session”可以是正常现象；若已有 `astrbot` 会话，改用下一节的 `attach`，不要重复启动。

```sh
tmux new-session -s astrbot 'proot-distro login ubuntu -- /bin/sh /root/start-astrbot.sh'
```

这是长期运行窗口。首次账号/密码以**当次启动信息**为准，私下记录并在登录后立即修改；不要在录屏里展示日志中的凭据。手机浏览器打开 `http://127.0.0.1:6185/`，确认能登录。

✅ 页面可达、服务没有退出、日志没有启动失败。按 **Ctrl+B，松开，再按 D** 分离 tmux（不是 Ctrl+C）。回看使用：

```sh
tmux attach-session -t astrbot
```

`Ctrl+C` 会请求停止前台服务，`exit` 会退出当前 shell；分离 tmux 才是保持运行。若 tmux 因启动错误立即退出，先确认没有残留实例，再进入 Ubuntu、在 `/root/astrbot` 前台运行同一启动脚本查看错误，不要并行启动第二份。

printf '%s  %s\n' \

### 3.3 先检查 QQ 包；已知 404 必须停下来

**位置：Debian 的 `/root/napcat-installer`。**下面从已审查脚本中提取唯一 ARM64 `.deb` 地址，不猜下载路径；下载到 `.part` 后校验通过才改名。脚本失败会退出这一块，不会运行安装器。

```sh
(
  set -eu
  QQ_DEB_URL="$(grep -Eo 'https://qqdl\.gtimg\.cn/[^"[:space:]]+_arm64\.deb' NapCat-install-linux.sh | sort -u)"
  test -n "$QQ_DEB_URL"
  test "$(printf '%s\n' "$QQ_DEB_URL" | wc -l)" -eq 1
  curl --proto '=https' --tlsv1.2 -fL --retry 2 "$QQ_DEB_URL" -o QQ.deb.part
  file QQ.deb.part
  dpkg-deb --info QQ.deb.part
  test "$(dpkg-deb -f QQ.deb.part Architecture)" = arm64
  mv QQ.deb.part QQ.deb
  sha256sum QQ.deb > QQ.deb.sha256
  sha256sum -c QQ.deb.sha256
)
```

**本次核对的实际结果：**安装器目标版本为 `3.2.30-50828`；其 ARM64 旧地址 HEAD 返回 **404 / application/xml**。这是这条旧链接的观测，不是“官方所有 ARM64 包均不可用”。QQ Linux 官网及其直接引用的下载配置读取成功（200），公布了 **3.2.34 / 2026-09-24** 的 ARM64 新包；本执行网络对新包 HEAD、Range GET 和本机 curl 复核为 **403，正文 0 字节**，因此没有包格式、架构或运行成功证据。来源链与两种不同结果见[上游参考 S4](上游参考.md#s4-napcatarm64参数路径与已知下载阻塞)。

处理顺序：

1. 保留已装好的 Ubuntu/AstrBot 和 Debian，不删除环境、不重跑初始化。
2. 查看 [NapCat 安装器官方仓库](https://github.com/NapNeko/NapCat-Installer)是否修复，以及 [QQ Linux 官方下载页](https://im.qq.com/linuxqq/index.shtml)。不同网络可能有不同结果，但只要本机返回错误就不能继续。
3. 若拿到**可信官方来源、经当前 NapCat 版本确认兼容**的 ARM64 QQ 包，可在此目录私下放为 `QQ.deb`，再执行 `file`、`dpkg-deb --info`、架构检查和哈希记录。**官方最新版不自动等于兼容版本**；版本不同或来源/兼容性无法核实，就停下请求维护者确认，不自动换第三方重打包。
4. `.deb` 格式正确只证明可解析；自己算出的 SHA-256 只能查文件后续是否变化。有上游可信摘要时还应比对，没有就明确记录“未取得上游发布摘要”，不能说已验证签名。

不要运行 `--force` 解决下载失败。也不要在旧实例上换用官方 Termux 一键安装器当修复器：本次查看的脚本有初始化失败后删除 `napcat` 环境的分支，见[上游参考](上游参考.md)。

**可选：验证官网公布的新包，而不是凭文件名宣称兼容。**以下仍在 Debian 的安装器工作目录执行，只下载候选文件，不运行 QQ，也不改变安装器参数。本环境的 403 不代表你的网络必然相同；你本机下载仍失败时必须停止。

```sh
(
  set -eu
  curl --proto '=https' --tlsv1.2 -fL --retry 2 \
    https://qqdl.gtimg.cn/qqfile/QQNTV2/9.9.36/release/9ee04bef/QQ_3.2.34_260924_arm64_01.deb \
    -o QQ-official-arm64.deb.part
  file QQ-official-arm64.deb.part
  dpkg-deb --info QQ-official-arm64.deb.part
  test "$(dpkg-deb -f QQ-official-arm64.deb.part Architecture)" = arm64
  dpkg-deb -f QQ-official-arm64.deb.part Version
  mv QQ-official-arm64.deb.part QQ-official-arm64.deb
  sha256sum QQ-official-arm64.deb > QQ-official-arm64.deb.sha256
)
```

安装器实际支持的是**当前工作目录存在名为 `QQ.deb` 的文件时复用本地包**，不是 `--local-qq` 一类参数。只有来源/包检查通过，并明确接受“在全新实例进行尚未完成的兼容性试装”后，才继续下面这块；已有实例不要照用：

```sh
(
  set -eu
  test ! -e "$HOME/Napcat"
  test ! -e "$HOME/.config/QQ"
  test ! -e QQ.deb
  sha256sum -c QQ-official-arm64.deb.sha256
  cp QQ-official-arm64.deb QQ.deb
  sha256sum QQ.deb > QQ.deb.sha256
)
```

**版本风险：**固定安装器解包后仍以旧目标版本调用配置更新；如果已有 `$HOME/.config/QQ/versions/config.json`，会写入旧的 `baseVersion/curVersion/buildId`。对全新实例，源码在此文件不存在时跳过该写入，但这仍不证明新版 QQ 与 NapCat 能启动/登录。不能将候选包试装宣传成已修复、已兼容；格式/来源不明、已有数据或运行失败就停下，不盲改版本字段。

**先确认上一节通过，才在 Debian 执行本节。**本次选择官方发行包 `v4.18.28`，下列 SHA-256 来自该 Release 资产的 GitHub `digest` 字段，不是本教程编造的值。固定版本是为了可追溯，不代表后续永远不需要更新。

    -o NapCat.Shell.zip.part
  printf '%s  %s\n' \
    'bcdd8bdb9e44bd0cf6a90908e572141787fd9e98cb8d8eecc5adf25bbdcabb94' \

  unzip -t NapCat.Shell.zip.part
  mv NapCat.Shell.zip.part NapCat.Shell.zip

✅ 发行包摘要匹配、ZIP 测试通过。此处没有宣称已完成其与当前 QQ/手机的运行兼容测试；接下来实际启动才能验证。

### 3.5 执行 Shell 安装，而非 Docker 安装

**位置：Debian 同一目录，只适用于首次安装或经过备份审查的维护。**

```sh
(
  set -eu
  test -s QQ.deb
  test "$(dpkg-deb -f QQ.deb Architecture)" = arm64
  sha256sum -c QQ.deb.sha256
  printf '%s  %s\n' \

```

参数含义：`--docker n` 选 Shell 安装；`--cli n` 不装额外 TUI-CLI；`--proxy 0` 不用安装器内置下载代理。**本路线不用 `systemctl`、`service` 或 Docker Compose 管理服务**。PRoot 不是带 systemd PID 1 的完整虚拟机；不能通过“加 sudo”变成真正 root 容器。

安装器会安装系统依赖、解包 QQ、注入 NapCat。仅“脚本运行结束”不足以通过；检查是否有 apt、下载、解包、注入错误。固定快照的 QQ 路径为 **`$HOME/Napcat/opt/QQ/qq`**，`Napcat` 大小写不可改。升级后路径变化时停止核对，不猜。

```sh
test -x "$HOME/Napcat/opt/QQ/qq" && \
  file "$HOME/Napcat/opt/QQ/qq"
command -v xvfb-run
```

✅ 路径存在且可执行，架构与手机匹配，`xvfb-run` 存在。不要因安装结束提示就宣称 QQ 在线。

### 3.6 固定 NapCat 工作数据目录，限制 WebUI，再启动

**位置：Debian；仅适用于这个全新实例。**`v4.18.28` 支持 `NAPCAT_WORKDIR`，用来固定配置/日志目录。本教程设为 `/root/napcat-data`，不搬动 QQ 安装目录。已有实例不能直接改此变量，否则可能打开一份新的空配置；先查旧路径并备份。

```sh
python3 - <<'PY'
import json
from pathlib import Path
p = Path.home() / 'napcat-data' / 'config' / 'webui.json'
p.parent.mkdir(parents=True, exist_ok=True)
cfg = json.loads(p.read_text(encoding='utf-8-sig')) if p.exists() else {}
if not isinstance(cfg, dict):
    raise SystemExit('配置不是对象，停止；不要覆盖')
cfg['host'] = '127.0.0.1'
cfg['port'] = 6099
p.write_text(json.dumps(cfg, ensure_ascii=False, indent=2) + '\n', encoding='utf-8')
p.chmod(0o600)
print('WebUI 回环地址已设置；没有显示或上传登录凭据')
PY
```

```sh
(
  set -eu
  test ! -e "$HOME/start-napcat.sh"
  cat > "$HOME/start-napcat.sh" <<'SH'
#!/bin/sh

QQ_EXE="$HOME/Napcat/opt/QQ/qq"
test -x "$QQ_EXE"

  chmod 700 "$HOME/start-napcat.sh"

```

`--no-sandbox` 是该 Shell 启动方案使用的参数，不是“更安全”的选项；PRoot 也不隔离不可信插件。只装可信来源的软件，不把 WebUI 暴露公网。

```sh
exit
```

**回到 Termux。**确认没有同名会话/重复 QQ 实例后：

```sh
tmux new-session -s napcat 'proot-distro login napcat -- /bin/sh /root/start-napcat.sh'
```

✅ 看到 QQ/NapCat 实际启动及 WebUI 信息，没有立即崩溃。保留运行；Ctrl+B、松开、D 分离。以后回看用 `tmux attach-session -t napcat`。**不要用 `systemctl start napcat` 代替上面的启动命令。**

## 第 4 关｜本人登录 QQ，分别验收两个面板

1. 手机浏览器打开实际 NapCat WebUI 地址，通常为 `http://127.0.0.1:6099/`。Token 从**自己的本次运行提示或本地配置**私下取得；不要发给 AI、不要录进画面、不要套网上默认值。
2. 由本人扫码/完成账号安全确认。视频应暂停录制或用明确标注的示意图替代，**不得公开仍有效的二维码**。
3. 在 NapCat 当前页面确认账号是自己的测试号、状态为已登录且未离线。二维码消失、页面能打开、缓存显示账号，都不能单独作为在线证明。
4. 再打开 AstrBot 的 `6185` 面板并确认管理登录可用；管理密码、NapCat WebUI Token、OneBot Token、模型 API Key 是**四种不同用途的凭据**。

**位置：Termux，辅助检查，不输出页面正文。**

```sh
curl --noproxy '*' --connect-timeout 3 --max-time 5 \
  -sS -o /dev/null -w 'AstrBot HTTP=%{http_code}\n' http://127.0.0.1:6185/
curl --noproxy '*' --connect-timeout 3 --max-time 5 \
  -sS -o /dev/null -w 'NapCat HTTP=%{http_code}\n' http://127.0.0.1:6099/
```

HTTP 200 只说明网页响应；重定向/鉴权响应需结合页面核对；`000` 表示请求未得到正常 HTTP 响应。**这两条命令不查询 QQ 登录状态，也不测试 AI。**

```sh
ss -ltn | grep -E ':(6185|6099|6199)([[:space:]]|$)'
```

此时 `6199` 可能尚未配置，应在第 5 关后出现。面板监听应是 `127.0.0.1`（或你明确配置的回环地址），不能是 `0.0.0.0`、`*`、`[::]`。某些 Android 限制 socket 枚举，`ss` 报权限错误时**不能据此断定没监听**，需结合应用启动信息和私下的配置检查；未核实前不宣称“仅本机可见”。

## 第 5 关｜反向 WebSocket：AstrBot 作服务端，NapCat 作客户端

本节按[官方 OneBot 文档](https://docs.astrbot.app/platform/aiocqhttp.html)说明字段含义；不同版本菜单可能变化，以自己的界面和字段为准，不伪造当前 UI 截图。

### 5.1 先配置 AstrBot

在管理面板找到机器人/平台适配器配置，创建 **OneBot v11** 实例：

| 字段含义 | 本教程填写方式 |
|---|---|
| 实例 ID | 自己取唯一名称，例如 `phone-qq`，不是 QQ 密码 |
| 启用 | 开启 |
| 反向 WS 监听主机 | `127.0.0.1`；同手机两 PRoot 共享网络，不必照搬面向跨主机的 `0.0.0.0` 示例 |
| 反向 WS 监听端口 | `6199`；占用时另选空闲端口并同步另一端 |
| 反向 WS Token | 自己生成的高熵随机值，私下保存；不是面板登录 Token |

保存，等待配置生效；按该版本提示重载/重启时先记录影响，不能边重启边当作连接稳定。不要开启多个同端口适配器。

### 5.2 再配置 NapCat

在当前账号的 OneBot 网络配置中创建/启用 **WebSocket 客户端（反向 WS）**，不是 WS 服务端，也不是 HTTP 服务：

```text
ws://127.0.0.1:6199/ws
```

填写与 AstrBot **完全相同**的 OneBot Token，启用并保存。`/ws` 不能漏；不要把 `6099`、`6185` 或 `0.0.0.0` 当目标地址。确认该配置属于当前正在登录的账号/实例。

✅ 在**本次操作后的新增日志**中找到真实的 OneBot 适配器连接，核对 NapCat 客户端状态；当前官方文档示例为 `aiocqhttp(OneBot v11) 适配器已连接`。历史日志里曾经出现过一次不代表现在仍连接。HTTP `101` 是 WebSocket 升级状态，但某些版本不以该格式记日志；不能仅靠匹配 `101` 判断成败。

没有通过：先查 QQ 在线 → AstrBot 已监听 → 客户端方向/地址/Token → 两端新增错误，参见[故障排查](安全与故障排查.md)。不要通过删配置、取消鉴权来“试通”。

## 第 6 关｜模型配置、触发规则、真实消息：分层验收

### 6.1 配置模型，不索取或展示密钥

参照 [AstrBot 模型配置文档](https://docs.astrbot.app/providers/start.html)，在自己的面板完成：

1. 选择服务商/兼容接口类型；Base URL 和模型 ID 来自**该服务商当前官方说明/账户可用列表**，不能照抄视频里随意编写的值。
2. 本人填写 API Key，保存并测试。留意网络、额度、模型权限与超时；不要把 Key 放进聊天、启动命令参数、GitHub 或录屏。
3. 在这个机器人实际使用的配置中选择该对话模型，保存。创建了提供商但没有给当前实例选用模型，仍可能无法对话。
4. 先不装额外插件、不开放系统命令/文件工具，减少变量；模型测试通过后再逐个增加功能。

### 6.2 用另一个账号发一条无隐私消息

先确认当前配置的触发规则：私聊是否响应、群聊是否要求 @/前缀、是否有允许列表。不要为拍演示直接开启所有群/所有人。

由本人用另一个测试 QQ 号，在允许的私聊或自己管理的测试群中发送一条无隐私请求，例如“请用两句话解释什么是回环地址”。若当前规则要求 @机器人或前缀，按规则发送；**不要虚构一个所有版本通用的测试命令**。

| 验收层 | 必须分别看到的证据 |
|---|---|
| 面板层 | 本机两个页面可达、管理认证可用 |
| 账号层 | QQ 已登录且未离线 |
| 协议层 | 当次新增日志中的 OneBot 连接 |
| 入站层 | AstrBot 收到这一条消息，时间/消息标识能对应 |
| 模型层 | 选定模型确实被调用，成功结束；仅“模型配置保存成功”不算 |
| 出站层 | 日志中的发送结果与另号实际收到的回答一致 |

✅ 所有需要宣称的层均通过，才写“这次新装已跑通/AI 回复已验收”。收到 `/help`、固定规则或插件回复只能证明对应功能，不能自动归因于模型。发布证据只保留脱敏摘要，不贴聊天原文、账号或完整请求响应。

**本仓库现状：全新手机按这条公开路线端到端验收尚未完成，AI 生成独立验收尚未完成。**原机迁移实例的历史消息反馈不能替代本节。

## 第 7 关｜日常恢复、保活与可选开机入口

### 7.1 先分清首次安装和恢复

| 场景 | 应做 | 不应做 |
|---|---|---|
| 首次安装 | 第 1—6 关逐项验证 | 跳过失败继续安装 |
| 仅切到别的 App | 原会话继续运行；必要时 `tmux attach` | 再开一份同端口服务 |
| 服务异常退出 | 先检查具体会话/错误，修复后从固定目录启动原实例 | 再执行 `init`、清空 data、重装 QQ |
| Android 重启后 | 原进程已消失，从原环境/原目录恢复，再查 QQ/OneBot | 再次 `proot-distro install` |
| 更新版本 | 维护停机、备份、单组件更新、验收/回滚 | 同时升级全部组件且没有恢复点 |

**位置：Termux。**

```sh
tmux list-sessions
proot-distro ps
```

`proot-distro ps` 是本文核对的 v5.9.0 命令；旧版不支持时不要套用。会话存在不等于服务健康：先 attach 检查，不对一个仍运行的实例重复执行启动。

当确认相应实例已停止且没有其他守护脚本管理它时，用第 2.4 / 3.6 节的 `tmux new-session ...` 命令恢复，或用下一节的受限启动入口。QQ 可能需要本人重新认证，不能把面板可达当作自动登录成功。

### 7.2 保活不是永不掉线

**位置：Termux。**

```sh
termux-wake-lock
```

按自己手机系统设置允许 Termux/Termux:Boot 后台运行、自启动，并评估电池优化限制；厂商菜单名称不同，视频不要冒充通用逐按钮操作。wake lock、tmux 都不能保证 Android 不清理进程，也不能解决断网、过热、账号安全挑战。停止整套服务且不再需要保活时执行 `termux-wake-unlock`。

### 7.3 可选：创建本教程的幂等启动入口

**只用于已通过手动启动的新装实例**，路径和会话名称须与本文一致；旧部署有其他启动器时不要再装一套。本例不处理扫码、不请求快速登录接口、不发送 QQ 消息，也不检查模型。

**位置：Termux。**存在同名文件就停止检查，不能覆盖已有部署。

```sh
(
  set -eu
  mkdir -p "$HOME/bin" "$HOME/.cache"
  test ! -e "$HOME/bin/start-phone-bot"
  cat > "$HOME/bin/start-phone-bot" <<'SH'
#!/data/data/com.termux/files/usr/bin/bash
set -euo pipefail
umask 077
export PATH="/data/data/com.termux/files/usr/bin:$PATH"
mkdir -p "$HOME/.cache"
exec 9>"$HOME/.cache/phone-bot-start.lock"
flock -n 9 || exit 0
# 在持锁后检查，避免维护标记设置与启动之间发生竞争。
if [ -e "$HOME/.phone-bot-maintenance" ]; then
  printf '处于维护状态，不启动服务。\n'
  exit 0
fi
termux-wake-lock
for name in astrbot napcat; do
  if tmux has-session -t "=$name" 2>/dev/null; then
    printf '%s 会话已存在；仍须检查服务健康。\n' "$name"
    continue
  fi
  if [ "$name" = astrbot ]; then
    container=ubuntu
  else
    container=napcat
  fi
  # 关闭子进程的锁描述符，避免长期服务继承并一直占锁。
  tmux new-session -d -s "$name" \
    "proot-distro login $container -- /bin/sh /root/start-$name.sh" 9>&-
done
printf '已请求启动；请分别核验面板、QQ、OneBot、消息和模型。\n'
SH
  chmod 700 "$HOME/bin/start-phone-bot"
  bash -n "$HOME/bin/start-phone-bot"
)
```

先在 Termux 手动执行并验收：

```sh
"$HOME/bin/start-phone-bot"
```

该入口只防止通过**同一入口/同名 tmux 会话**重复拉起，不能识别所有外部守护进程或修复“会话还在但程序已卡死”。退出码 0 也可能只是维护中/已有会话，**不是机器人健康证明**。不要与旧机恢复脚本叠加运行。

### 7.4 可选：接入 Termux:Boot

1. 安装与 Termux 签名兼容的 Termux:Boot；**点开插件图标至少一次**，按 [官方 README](https://github.com/termux/termux-boot#how-to-use)激活。
2. 确认 7.3 的本机启动入口已经手动验证；不能靠手机重启来掩盖当前报错。
3. **位置：Termux**，仅新建这个入口：

```sh
(

  mkdir -p "$HOME/.termux/boot"
  test ! -e "$HOME/.termux/boot/50-phone-bot.sh"
  cat > "$HOME/.termux/boot/50-phone-bot.sh" <<'SH'
#!/data/data/com.termux/files/usr/bin/sh
umask 077
# 缓冲时间不是网络就绪或 QQ 已登录的证明。
sleep 20
"$HOME/bin/start-phone-bot" >> "$HOME/.phone-bot-boot.log" 2>&1
SH
  chmod 700 "$HOME/.termux/boot/50-phone-bot.sh"
  sh -n "$HOME/.termux/boot/50-phone-bot.sh"

```

这只是文档中的**新装启动范例，未在全新手机实测**，并非原机那套含登录查询/有界重试的私有恢复脚本。开机日志只记录启动请求结果，应用日志仍在相应会话/实例；日志也按私有文件保管。

### 7.5 自动登录与整机重启必须另外验收

- 首次 QQ 登录由本人完成。NapCat 的 `autoLoginAccount`/启动环境覆盖项只能指定账号，不能创造有效授权会话；是否能自动登录取决于保留的会话和平台安全状态。设置时用自己的版本支持方式，**不在公开脚本里写账号/密码**。
- 本轮不建议加入密码回退、无限登录重试或清空会话“修复”。有界恢复原理及已核验记录见[开机自启与 QQ 自动登录](开机自启与QQ自动登录.md)。
- 经机主同意后，先测试 **NapCat/QQ 服务重启**：确认原本在线 → 真正停止并确认离线 → 恢复 → 不点 UI/不扫码地确认在线 → 查新增 OneBot 连接。测试中手动登录就不能算免点击。
- **Android 整机重启是另一项测试**：授权后重启，记录是否需解锁、是否手动打开 Termux、系统是否实际触发入口、QQ 是否需认证、OneBot 和消息是否恢复。有人手动执行启动脚本就不能写“开机自启已通过”。
- 2026-10-02 现有隔离实例只完成一次 NapCat/QQ 服务重启免点击登录，整个测试 136 秒；**未重启 Android、未复测消息/AI**。136 秒不是保证的登录耗时。历史私有镜像迁移记录不是本教程新装成功录像。
