# 开机自启与 QQ 自动登录

> 2026-10-03 整理；实机验证日期为 **2026-10-02**。本文公开现有部署的恢复机制、配置检查点和脱敏验收结果，**不是可直接安装的通用自启脚本包**。新手机先完成[从零安装与连接](从零安装与连接.md)，再按自己的实例适配恢复入口。

## 1. 先区分三个环节

1. **Android 开机触发**：系统允许 Termux 在开机后执行入口。安装来源、系统后台限制和网络就绪状态需要在自己的设备核对；不要混装签名不同的插件。
2. **服务恢复**：入口调用恢复脚本，启动正确的 AstrBot 与 NapCat/QQ 实例，避免重复拉起已运行的进程。
3. **QQ 自动登录**：NapCat 使用机主已授权且仍有效的本地会话快速登录，随后核验 OneBot 连接。

服务启动成功不等于 QQ 已登录，QQ 在线不等于协议连接或消息回复成功。手动调用开机恢复脚本也不等于 Android 已实际触发开机入口。

## 2. 自动登录的前提与配置

- 先由机主在本机完成首次登录/安全验证，保留该实例的会话数据。自动登录不是绕过扫码、授权或账号风控，也不需要把 QQ 密码写进脚本。
- 确认运行中的 NapCat 实例及其实际配置路径。不要把另一实例、旧备份或另一安装目录里的配置当成当前配置。
- 本次实机的 `webui.json` 已保存非空的 `autoLoginAccount`。编辑前私下备份完整配置，**只修改目标字段，保留其余内容**；账号由机主在设备上填写，不粘贴到公开 issue，也不要用示例空配置覆盖原文件。
- 在该机已安装版本源码中，账号选择逻辑为 `process.env.NAPCAT_QUICK_ACCOUNT || Nt.getAutoLoginAccount()`，随后调用 `requestQuickLogin(account)`。因此还要核对启动环境中的 `NAPCAT_QUICK_ACCOUNT` 是否覆盖了配置值。这是已检查安装版本的行为，**不是所有版本的接口承诺**；不同版本须核对自己的安装源码和[上游参考](上游参考.md)。
- 配置与会话备份保持私有；本次配置权限已核验为 `0600`。不要打印整个配置检查字段，也不要把会话文件、账号值、WebUI Token 或 OneBot Token 提交到 GitHub。

只有“账号字段非空”或“快速登录列表有账号”不能证明登录成功，最终必须看实际登录状态。

## 3. 本次部署的恢复策略

已部署链路：Termux 开机入口 → `boot_restore_services.sh --boot` → 核心服务恢复 → 离线时调用 `napcat_auto_quick_login.py`。

- 开机模式先延迟约 20 秒；延迟只是缓冲，不能保证网络必然就绪。
- 使用 `boot_restore.lock` 串行化恢复，避免开机触发和手动维护并发启动。
- 核验进程身份和实例状态；已运行的 AstrBot 不重复启动、不为登录恢复而重启。
- 检测 QQ 离线时进行有界快速登录重试：最多 12 次、间隔 10 秒；已经在线则返回 `already_login`，不反复发起登录。
- 每次恢复都独立核验 QQ 状态与真实 OneBot 连接；管理页 HTTP 200 仅是管理服务可达的辅助证据。
- 重试耗尽或出现需要人工验证的情况，保留私有诊断记录并交由机主处理，不无限循环、不盲目改 Token、不删除会话强行重登。

以上文件是原机现有部署中的组件，**本仓库没有分发这些私有实例脚本**。下面只说明控制流程，不能复制到终端执行：

```text
取得恢复锁；无法取得则按约定等待或退出
若为开机触发：等待启动缓冲时间
按实例检查并幂等恢复 AstrBot、NapCat/QQ
最多尝试 12 轮：
    若实际登录状态在线：结束登录重试
    否则：使用该实例的授权会话请求快速登录
    等待后再次查询状态；失败记录留在私有目录
独立检查 QQ 在线与 AstrBot OneBot 适配器连接
输出脱敏状态；未通过则报告失败，不冒充验收成功
释放恢复锁
```

为新设备落地时，应先确定该安装来源支持的开机触发方式，再把**已验证的本机启动命令、工作目录、环境变量和配置路径**接入恢复脚本。不要直接套用原机私有路径、旧版恢复脚本或不明安装器命令。锁的持有/释放范围要明确；维护脚本与恢复脚本不能互相等待同一把锁而死锁。

## 4. 如何验证，而不是只看面板

### A. 服务重启测试（会短暂断开 QQ，先取得机主同意）

1. 只读预检：QQ 原本在线，两个管理服务可达，记录 AstrBot 与 NapCat 的进程身份、启动标识和日志基线。未通过就停止。
2. 私下备份配置及必要的会话和诊断信息，限制访问权限。
3. 只停止经过进程身份与父子关系核验的 NapCat/QQ 进程；不使用宽泛的进程名强杀，不停止 AstrBot。
4. **确认 NapCat/QQ 确实已停止且服务离线**，避免把旧在线状态误判为重启成功。
5. 调用已验证的恢复脚本，全程不打开登录界面、不点登录、不扫码。
6. 独立查询 QQ 登录/离线状态，检查 NapCat 进程已更换、AstrBot 仍是原进程，并在本次新增日志中寻找真实 OneBot 适配器连接。
7. 测试异常时尝试安全恢复并报告失败。不要仅凭恢复脚本退出码判定成功。

### B. 整机重启测试（单独授权、单独记录）

在确保有本机恢复手段后重启 Android，检查入口是否由系统触发、核心服务是否自行启动、网络是否就绪、QQ 是否无需人工介入上线及 OneBot 是否连接。不能把 A 项通过替代 B 项。

若还要验证消息/AI 回复，须另获机主同意后用另一测试号发送无隐私消息，按[验收记录模板](验收记录模板.md)逐层记录。不要为了提交文档擅自重启手机或发送消息。

该版本出现了明确的 `aiocqhttp(OneBot v11) 适配器已连接` 日志。HTTP 101 通用日志匹配为零是日志格式差异，不代表没有连接；上述关闭/错误计数为零也不代表已穷尽所有错误类型。

恢复早期，快速登录助手曾返回 `failed_auth`，后续变为 `already_login`；最终状态接口确认在线，原生快速登录成功计数为 1。**中间状态的原因未单独诊断**，不能直接归因为 Token 错误或限流，也不能声称助手的每次调用都成功。

## 6. 明确没有证明的事项

- **本轮没有重启 Android 整机**，因此没有重新验证系统开机调度和冷启动网络条件。
- 本轮没有发送 QQ 消息，也没有重新验收 AI 模型回复或插件功能。
- 仅有一次服务重启测试，不代表跨多次重启的稳定性，更不保证会话永久有效。
- 原机使用私有备份提取后的隔离实例，不是公开零镜像教程在全新手机上的端到端复现。
- 2026-09-25 的历史整机重启曾恢复服务但需要手动登录 QQ，该历史结果仍保留，不改写成自动登录成功。
